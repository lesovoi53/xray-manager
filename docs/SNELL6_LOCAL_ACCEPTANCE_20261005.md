# Snell v6 default: локальная проверка

Дата: 5 октября 2026. Результат: **32/32 проверки прошли**.

Проверен существующий `singbox-extended-check.exe` из рабочего дерева TUNA:

- Версия: `1.14.1-extended-2.7.2`, Go 1.26.4, Windows amd64, CGO disabled.
- SHA-256: `af077ab347fa8bbd5ab31b4e0310f2979adb3ed3d95f53872091d25219ca06a7`.
- Два независимых процесса одного бинарника: SOCKS → Snell v6 client → Snell v6 server → локальный тестовый сервис.
- Режим `default`, PSK-only, `reuse=false` и `reuse=true`.
- Все listener привязаны к 127.0.0.1, серверный маршрут принудительно ограничен loopback. Внешняя сеть и VPS не использовались. Настройки рабочих служб не читались и не менялись.

## Фактические результаты

| Проверка | Успех |
|---|---:|
| HTTPS по IPv4, проверка сертификата и точного тела 81920 байт | 6/6 |
| HTTPS с доменным SOCKS-назначением и SNI `snell.test`, проверка сертификата | 6/6 |
| UDP DNS A: transaction ID, флаги ответа и ожидаемый адрес | 6/6 |
| UDP DNS AAAA: transaction ID, флаги ответа и ожидаемый адрес | 6/6 |
| STUN Binding: transaction ID, success response, XOR-MAPPED-ADDRESS | 6/6 |
| Неверный PSK: HTTPS не проходит, прямого клиентского fallback нет | 2/2 |

Для каждого reuse выполнено три серии. Итоговый запуск занял 4,56 с; это короткая функциональная проверка, не тест стабильности. Проверка нативной конфигурации выполняется перед каждым запуском, но в 32 сетевых результата не засчитывается. Процессы завершены, временные конфигурации и тестовый закрытый ключ TLS удалены. Логи и машиночитаемый результат сохранены отдельно в `snell6-local-acceptance-20261005-final/` в родительском workspace; JSON продублирован рядом с этим отчётом.

STUN обслуживает контролируемый локальный fixture, это не проверка внешнего NAT. DNS-запросы идут через настоящий UDP relay к локальному DNS fixture; AAAA проверяет содержимое ответа, не IPv6-транспорт. Для HTTPS по имени серверное правило заменяет адрес назначения на loopback: внешнее DNS-разрешение сервером этим не проверено. TCP проверен передачей HTTPS, отдельный half-close/нагрузочный тест не выполнялся.

## Формат ссылки для реализации

Синтетический пример, не рабочие реквизиты:

```text
snell://synthetic-local-only-0123456789abcdef@192.0.2.1:20000/?version=6&mode=default&reuse=true&udp-relay=true#Snell6-local-example
```

Ключевые поля: `version=6`, `mode=default`, PSK, имя, адрес и порт. Obfs-поля отсутствуют, `quic-proxy-mode=true` не выдаётся. Формат сопоставлен с ранее прочитанным `VpnConfig.kt`; новая Kotlin/Android проверка импортера в этом этапе не запускалась. Стенд задаёт эквивалентный native JSON напрямую.

## Вывод для следующего этапа

Реализация Snell v6 default в имеющемся extended-core умеет передавать TCP и обычный UDP между своими клиентской и серверной сторонами с обоими значениями reuse. Это позволяет использовать её как кандидата для отдельной серверной службы, сохранив официальный v5.

Следующий обязательный шаг — получить закреплённую Linux amd64 сборку с проверяемым происхождением и выполнить этот же тест на Debian 12/13. Совпадение версии в строке `version` недостаточно: нужно связать бинарник с commit, зависимостями и overlays. Затем проверяются Xray gateway TCP/UDP, установщик/повтор/обновление/откат и конкретный Android APK.

**Не проверены:** Linux/Hydracore/официальный сервер v6, Debian systemd, пользовательский `userkey`, unshaped/unsafe-raw, QUIC Proxy, маршрутизация Xray, внешний интернет, реальный Android и длительная работа. Windows self-interoperability не выдаётся за совместимость любых Snell-серверов.
