# Яндекс Волга: настройка и обслуживание серверной части

Документ для выпуска **v2026.09.29.1**, Debian 12/13 amd64. Клиент TUNA развивается отдельно. Служба OpenFlux на VPS не создаёт VPN-интерфейс телефона.

## Что добавлено

- Транспорт `vyandex` доступен в настройке каналов и каталоге OpenFlux v2.
- Classic использует один документ на группу; Multi-Stream — от одного до четырёх. Всего доступно восемь серверных экземпляров.
- В режиме Xray оба вида выходного трафика проходят через сохранённый SOCKS5: TCP через CONNECT, UDP через UDP ASSOCIATE. Отказ прокси не переключает выход автоматически на Direct.
- Проверка документа включает авторизацию и WebSocket, а не только HTTP-ответ страницы. Конфигурация меняется после успешной проверки; при неудачном запуске возвращается предыдущая.
- Cookies обновляются непосредственно на VPS; есть ручной импорт и инструкция SSH-туннеля на случай SmartCaptcha.
- Обновление токенов relay согласовано с WebSocket; 401 вызывает ограниченную повторную авторизацию, а не бесконечную отправку с недействительным токеном.
- Просмотр экспортируемого bundle читает поля из `payload`, как и сам URI. Это исправляет ложные значения `OpenFlux / classic / 0 групп`.

## Требования и настройка

1. В аккаунте владельца включите **новый редактор Яндекс Волга**, создайте тестовый документ и разрешите редактирование по ссылке. Ссылка на OnlyOffice не становится Волгой от смены названия транспорта.
2. Откройте `x-openflux` → «Каналы» и настройку нужного канала. Выберите Волгу. В Multi-Stream укажите до четырёх разных HTTPS-ссылок `disk.yandex.ru` или `docs.yandex.ru`.
3. Сохраните согласованные с клиентом кодек и ключ. Не переключайте их ради устранения ошибки авторизации.
4. Укажите Xray или осознанно выберите Direct. Для Xray требуется работающий SOCKS5 с TCP и UDP; порт берётся из `/etc/x-manager/gateways.env`.
5. После успешной проверки и запуска обновите каталог OpenFlux в TUNA и выберите нужные группы для пользователя. Серверный канал, запись каталога и выбор пользователя — разные состояния.
6. Проверьте экспорт: имя, `multistream`, число групп и URL. Четыре документа одного канала — одна группа с четырьмя URL, а не четыре группы.

Конфигурация канала хранится в `/etc/openflux/instances/N.env`. Пароли, ключи и документы не следует передавать в командной строке, коммитах или публичных логах. Runner передаёт документы через открытый файловый дескриптор и `--url-file`.

## Cookies без постоянно работающего ПК

В разделе «Настройки» → «Cookies Волги» доступны:

| Действие | Результат |
|---|---|
| Получить и проверить сейчас | Запуск `volga-cookies.service`: HTTP-обновление с имеющейся сессией и проверка всех настроенных документов |
| Включить автообновление | `volga-cookies.timer`, примерно раз в 30 минут, первая попытка после загрузки через 5 минут |
| Отключить автообновление | Останавливает таймер; работающие каналы сохраняются |
| Состояние и журнал | Результат последнего запуска и расписание |
| Импортировать файл на VPS | Netscape cookies, только домены Яндекса, закрытый файл с резервной копией |
| Инструкция SSH-туннеля | Команды для браузера, использующего внешний IP этого VPS |

Установщик доставляет units, но **не включает таймер на новой установке автоматически**: без документов и принятой сессии обновлять нечего. Уже включённый таймер сохраняется.

Файл: `/etc/openflux/yandex-cookies.txt`, доступ группе `openflux`, без доступа остальным пользователям. При обновлении сначала проверяются новые cookies; только после успеха файл атомарно заменяется. Предыдущая версия сохраняется как `yandex-cookies.previous.txt`. В запущенных каналах новые cookies используются при следующей авторизации; каналы не перезапускаются таймером.

Пустое поле срока действия и `0` в Netscape означают сессионные cookies; они поддерживаются обеими частями реализации. Автообновление не гарантирует бессрочную сессию: Яндекс может потребовать ручную SmartCaptcha. В этом случае задача завершается ошибкой и оставляет последний файл.

### Ручная SmartCaptcha через SSH

На компьютере оставьте работающим туннель (замените параметры сервера):

```bash
ssh -N -D 127.0.0.1:18791 -p SSH_PORT -o ExitOnForwardFailure=yes -o ServerAliveInterval=30 root@SERVER
```

Сверьте SSH-отпечаток. Если локальный порт занят, выберите другой и используйте его в помощнике. Это временный локальный SOCKS-порт; публичный порт на VPS не открывается.

В другом окне Windows PowerShell:

```powershell
scp -P SSH_PORT root@SERVER:/usr/local/share/x-manager/scripts/volga-cookie-capture.ps1 .
powershell -NoProfile -ExecutionPolicy Bypass -File .\volga-cookie-capture.ps1 -ServerHost SERVER -SshPort SSH_PORT -SocksPort 18791
```

Помощник открывает отдельный Chrome, ждёт ручного открытия документа и подтверждения, получает cookies Яндекса, включая HttpOnly, и передаёт их по SSH. Затем запустите проверку cookies в серверном меню. После завершения закройте браузер и туннель, удалите временный профиль по показанному пути. Не присылайте cookies в чат.

Интерактивный проход именно нового Windows-помощника ещё не включён в приёмку: проверен его синтаксис. Ранее ручной браузерный путь через VPS проверялся отдельно. На телефоне нужны SSH-клиент с динамическим SOCKS, поддерживающий прокси браузер и экспорт Netscape с HttpOnly; универсальной команды для всех приложений нет.

## Ограниченные перезапуски — TUNA Watchdog

Главное меню → «Обновление и восстановление» → «TUNA Watchdog». Выберите установленную службу, лимит повторов и задержку. Доступны отключение перезапусков, журнал и явный сброс лимита с запуском.

Это политика systemd, без постоянно работающего дополнительного демона:

```ini
[Unit]
StartLimitIntervalSec=infinity
StartLimitBurst=4
[Service]
Restart=on-failure
RestartSec=30s
```

Пример допускает первый запуск и три повторные попытки. Диапазон настройки: 0–20 повторов, задержка 1–3600 секунд. Политика записывается в `/etc/systemd/system/UNIT.service.d/90-tuna-watchdog.conf`, перед заменой создаётся копия. Применение проверяет итоговые свойства systemd и не перезапускает работающую службу.

Обычный `systemctl stop` не вызывает автоматического запуска. Лимит учитывает также ручные старты; после достижения лимита нужен `reset-failed` и запуск либо действие меню. Перезагрузка VPS сбрасывает счётчики. Watchdog реагирует на аварийное завершение процесса, **не проверяет зависание, доступность сайта или качество VPN**. Обычный успешный выход процесса не перезапускается при `on-failure`.

Установка не меняет политики всех существующих служб автоматически. Сохранённые drop-in продолжают действовать. Если другой override перекрывает выбранные параметры, помощник сообщает ошибку и восстанавливает свою предыдущую настройку.

## Диагностика по слоям

| Наблюдение | Что проверить |
|---|---|
| OnlyOffice вместо Волги | Новый редактор и права владельца документа |
| SmartCaptcha / нет авторизации | Cookies и ручной браузер через IP того же VPS |
| 401 relay | Состояние авторизации и повторного соединения; не менять кодек или ключ |
| Auth/WS успешны, трафика нет | Совпадение документов, кодека и ключа с клиентом; затем счётчики реального peer-трафика |
| TCP работает, UDP нет | UDP ASSOCIATE и обратный UDP-путь SOCKS5/Xray; один успешный HTTP-запрос недостаточен |
| Все службы active, телефон не подключается | Отдельно создание TUN и hev-socks5-tunnel на клиенте; active на VPS не доказывает успех телефона |
| Служба исчерпала попытки | Причина в журнале, затем явный сброс лимита; не отключать ограничение ради маскировки сбоя |

```bash
systemctl status openflux@N --no-pager
journalctl -u openflux@N -n 80 --no-pager
systemctl show openflux@N -p MainPID -p NRestarts -p Result
systemctl show volga-cookies.service -p Result -p ExecMainStatus
systemctl list-timers volga-cookies.timer --no-pager
```

Перед пересылкой журналов удалите URI, токены, ключи, cookies и частные адреса. Успех preflight подтверждает вход в облачный документ; сквозной TCP/UDP требует отдельного клиента и проверки назначения.
