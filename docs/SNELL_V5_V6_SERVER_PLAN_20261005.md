# План серверной поддержки Snell v5/v6 для TUNA rc40

Дата исследования: 5 октября 2026. Статус: **план, реализация не начата**.

## Решение

Сохранить официальный Snell 5.0.1 и все действующие установки. Добавить отдельно включаемый сервер v6 с проверенной реализацией, затем расширить настройки и единый генератор подписок. Полный HYDRA-ULTIMATE устанавливать не требуется: его панель, управление пользователями и общий sing-box не нужны для этой задачи.

Для обычного v6 кандидат — официальный сервер; для полного контракта с `userkey` подтверждённый исходниками кандидат — реализация sing-snell в Hydracore/sing-box-extended. Сначала короткая изолированная квалификация этих вариантов. Рекомендуемая основа полного набора — отдельная служба на закреплённом extended-core с Snell inbound, без замены Xray и без переноса инфраструктуры HYDRA. Выбор конкретного выпуска ядра завершить после проверки совместимости, а не по номеру версии в README.

**QUIC Proxy не входит в подтверждённую поддержку v6.** Официальный v6 его удалил; исследованный Hydracore не создаёт Snell UDP listener. Клиентский переключатель сам по себе не добавляет серверную реализацию. Это отдельный блокирующий вопрос совместимости для данной функции, но не для обычного TCP/UDP relay v6.

## Что действительно делает HYDRA

1. [Плагин Snell](https://github.com/gr33nimax/HYDRA-ULTIMATE/blob/e74a90b6c1d0478db81e5b1261f39af200d40f8a/hydra/plugins/snell/plugin.py) создаёт отдельный inbound, PSK и порт для каждого разрешённого пользователя. Версии сервера — 5 или 6; outbound клиента — соответственно 4 или 6. PSK выводится через существующий механизм derive_hex_key; уже выданные порты сохраняются. Это модель HYDRA, её нельзя применять к нашим старым пользователям с заменой их ключей.
2. Там же: v5 получает `obfs_mode`; v6 — `mode`. Плагин открывает TCP диапазон 32000–32999, не UDP. Он не задаёт `network` в inbound. Пользователи включаются в итоговую конфигурацию по разрешению; методы добавления сохраняют реквизиты, конфигурация формируется заново из состояния. Его URI использует `obfs`, тогда как наш контракт требует `obfs-mode`. Прямое копирование генератора несовместимо с TUNA.
3. [Установка ядра](https://github.com/gr33nimax/HYDRA-ULTIMATE/blob/e74a90b6c1d0478db81e5b1261f39af200d40f8a/hydra/core/singbox.py) получает `hydracore-vps-linux-<arch>.tar.gz` из `gr33nimax/hydracore`, выбирая выпуск канала; проверяет ELF и идентичность выпуска, заменяет бинарник атомарно. [Загрузчик](https://github.com/gr33nimax/HYDRA-ULTIMATE/blob/e74a90b6c1d0478db81e5b1261f39af200d40f8a/hydra/utils/downloader.py) проверяет SHA-256; рассматриваемый путь требует digest. Для нашего установщика вместо плавающего канала нужен точный выпуск и хэш.
4. [Systemd-шаблон](https://github.com/gr33nimax/HYDRA-ULTIMATE/blob/e74a90b6c1d0478db81e5b1261f39af200d40f8a/hydra/core/singbox_units.py) запускает общий sing-box от root. В `singbox.py` есть `check -c` и проверки активности. Это не основание запускать наш отдельный Snell от root или заменять общую службу.
5. Минимальная проверка плагина — ветка extended 1.14.0. Она не доказывает наличие всех нужных возможностей в произвольном бинарнике: обязательны проверка схемы и передача данных.

Реальный сервер находится не в Python-плагине:

- [Hydracore option/snell.go](https://github.com/gr33nimax/hydracore/blob/5f4f2b74d04b1bec05ee193c3672d327fba7ce97/option/snell.go): inbound 5/6, PSK, массив `users` с `name`/`userkey`; для v5 obfs, для v6 mode. `quic_proxy_mode` отсутствует.
- [protocol/snell/inbound.go](https://github.com/gr33nimax/hydracore/blob/5f4f2b74d04b1bec05ee193c3672d327fba7ce97/protocol/snell/inbound.go): вызывает `snellv5.NewService/NewMultiService` или `snellv6.NewService/NewMultiService`; принимает только TCP listener. Декодированные TCP и UDP передаются соответственно RouteConnectionEx и RoutePacketConnectionEx. Наличие UDP relay не означает UDP транспорт от клиента до сервера.
- [go.mod](https://github.com/gr33nimax/hydracore/blob/5f4f2b74d04b1bec05ee193c3672d327fba7ce97/go.mod): Go 1.26.4, `github.com/sagernet/sing-snell v0.0.0-20260829071736-20f2eaec77c3`; эту же версию модуля закрепляет клиент. Общая зависимость облегчает проверку, но не заменяет её.
- [include/registry.go](https://github.com/gr33nimax/hydracore/blob/5f4f2b74d04b1bec05ee193c3672d327fba7ce97/include/registry.go) регистрирует Snell inbound/outbound. Это настоящая серверная реализация, не только экспорт конфигурации.

Официальные [release notes Snell](https://kb.nssurge.com/surge-knowledge-base/release-notes/snell) подтверждают совместимость сервера v5 с клиентом v4, наличие QUIC Proxy в v5 и его удаление в v6. Для v6 режимы на обоих концах должны совпадать; `unsafe-raw` передаёт незашифрованные данные. На момент чтения опубликован v6.0.0rc2. [Описание v6](https://nssurge.com/blog/snell-v6/) предупреждает о возможных несовместимых изменениях бета-протокола. Автообновление на произвольный новый upstream недопустимо.

## Матрица клиента и серверных работ

Контракт проверен в `VpnConfig.kt`, `VpnEditorDraft.kt`, `CoreCapabilities.kt`, `SingBoxConfig.kt`, `SnellDestinationResolver.kt`, `IsolatedSnellResolver.kt`, `native/singbox/{dependency-overlay,source-overlay}.json`, `snell_quic_client.go`, `snell_quic_protocol.go` клиентского дерева.

| Возможность TUNA | Что требуется на сервере | URI | Изменения установщика/меню | Приёмка |
|---|---|---|---|---|
| v4/v5 | Сохранить официальный 5.0.1; клиент использует wire v4 | Существующее `version=5` сохраняется | Не переписывать старые ссылки в v4 только потому, что так делает HYDRA | Старый клиент и rc40, TCP и UDP |
| v6 | Совместимый v6 inbound, фиксированный build | `version=6&mode=default` | Отдельное включение backend/version; корректная генерация | Native roundtrip, затем Android |
| PSK, имя | Существующие PSK/tag; стабильная идентичность | Percent-encoding PSK и fragment | Один генератор для меню, TUNA и экспорта | Спецсимволы, пробелы, повторный запуск |
| none/http/tls в v5 | Согласованный серверный obfs | `obfs-mode=http&obfs-host=...` | Сохранить текущий формат; не использовать HYDRA `obfs` | Все три режима, mismatch отрицательный |
| v6 default/unshaped/unsafe-raw | Режим обеих сторон одинаков | `mode=...`, без любых obfs-полей | Отдельный выбор; default по умолчанию, unsafe-raw явно помечен как без шифрования | 3 режима × reuse on/off; raw только в изолированной сети |
| userkey | Поддержка MultiService и стабильная таблица ключей | `userkey=...` | Опциональные отдельные ключи; не выводить их из UUID и не ротировать при обновлении | Два пользователя; wrong/missing/revoked key |
| reuse | Сервер должен корректно обслуживать повторные потоки | `reuse=true/false` | Настройка выдаваемого клиента, не выдуманный INI-параметр сервера | Последовательные/параллельные потоки, idle, half-close |
| tfo | Согласованная поддержка ядра/ОС; клиент имеет отдельный compatibility gate | `tfo=true/false` | Сохранять опцию; не обещать активность только по URI | Проверить реально применённый outbound и handshake |
| network, udp-relay | UDP relay + рабочий маршрут его пакетов | `network=auto/tcp/udp`, `udp-relay=true/false` | Разделять фильтр клиента и серверный listener; исключить конфликт udp + relay=false | TCP-only, UDP-only, UDP DNS/STUN |
| QUIC Proxy | Нужен отдельный совместимый UDP обработчик | В rc40 разрешён флаг только с v6 | Не выдавать true для официального v6/исследованного Hydracore | Реальный QUIC Initial и UDP путь; UDP-over-TCP fallback не считается успехом |
| Surge-строка | Тот же набор параметров, принимаемый parser | `NAME = snell, HOST, PORT, psk=..., version=...` | Опциональный экспорт из той же модели; не отдельная логика параметров | Импорт строки/URI дают одинаковый профиль |
| DNS | Сервер разрешает домены и сохраняет политику Xray | Не добавлять несуществующие параметры Snell URI | Клиентские Android DNS/SOCKS исправления не переносить на сервер | HTTPS по домену и IP; UDP по домену и IP |

В rc40 v6 отвергает даже явно заданный `obfs-mode=none`; генератор должен удалить несовместимые поля, а не добавить их с пустым значением. Два alias QUIC с противоречивыми значениями отвергаются. Не менять version для обхода этой валидации.

## Почему недостаточно обновить бинарник

Текущий `scripts/snell-subscriptions.py` читает только порт, PSK, имя, obfs/host. Новый URI имеет жёсткое `version=5`, а `matches()` принимает только v5. `apply()` не знает backend, version, mode или userkey. `install.sh` всегда ставит архив Snell 5.0.1 и создаёт один `snell.service`.

В синтетической проверке без служб и сети:

- Существующий v5/http дал ожидаемые version=5, obfs-mode/http, host, reuse и tfo.
- Конфигурация с `mode=unshaped`, поданная текущему генератору, дала version=5 и потеряла mode.
- Та же ссылка с version=6 не прошла текущую проверку привязки.

Это проверка чистых функций, извлечённых из фактического Python-файла через AST, с временными файлами и синтетическим PSK. Полный установщик и v6 сервер этим не проверены.

## Предлагаемая архитектура

1. Старые `/etc/snell`, `snell.service`, бинарник 5.0.1 и привязанные ссылки остаются действующим v5.
2. v6 сначала добавляется как отдельное подключение на свободном разрешённом порту. Отдельные конфигурация, непривилегированный UID и служба предотвращают влияние на рабочий v5. Имена новых путей и службы закрепить при реализации, например `snell6.service`, `/etc/x-manager/snell6/`, `/usr/local/lib/x-manager/snell6/`.
3. Extended-core используется только для Snell. Его outbound направляется на наш существующий SOCKS5 Xray с TCP и UDP после проверки UDP ASSOCIATE, адресов ответов и правил маршрутизации. Direct — только явно выбранный режим. Не менять Xray или панель ради старта sidecar. Если SOCKS-путь несовместим, испытать отдельную интеграцию через существующие transparent gateways; это не повод молча переключать трафик на Direct.
4. Старый v5 сохраняет текущие TCP REDIRECT и UDP TPROXY. `snell-routing.py` привязан к UID `snell`, фиксированным цепочкам и одному порту; второй процесс нельзя просто запустить под тем же UID и повторно вызвать этот скрипт. При необходимости общего механизма сначала параметризовать владельца, цепочки, состояние и исключения, с тестом одновременных служб.
5. Выбор backend/version — серверный. Reuse/network/tfo/udp-relay — параметры выдаваемого клиентского профиля. В интерфейсе показать их раздельно.
6. Мультипользовательский v6: у каждого пользователя собственный userkey, общий PSK конкретного inbound, стабильный ID привязки. Не включать `users` для старого PSK-only endpoint: это может отключить старые клиенты. Удаление одного ключа не должно менять остальных.
7. Перевод существующего v5 на v6 — отдельная явная операция после испытаний; обычное «Обновить полный выпуск» её не выполняет. По умолчанию пользователь получает дополнительную v6-ссылку, не замену оригинала.

## Этапы и критерии перехода

### 1. Квалификация ядра и контракта — ориентир 0,5–1 рабочий день

Собрать таблицу кандидатов: официальный v6rc2, закреплённый extended-core, при необходимости исследованный Hydracore. Сначала проверить candidate build, `version`, схему, TCP/UDP и все modes с native клиента. Для полного варианта проверить MultiService/userkey. Выбрать один кандидат для выпуска; не поддерживать три backend без необходимости.

Записать SHA-256 архива, бинарника, конфигураций без секретов, toolchain, module sums, patches и лицензии. Не брать неподтверждённый тег latest. Собрать в отдельной CI/лаборатории amd64, VPS не обязан иметь Go. Отсутствие подходящего бинарника или прав распространения останавливает публикацию компонента, а не запускает непроверенную замену.

### 2. Модель, генератор, настройки — 1–2 дня

Сначала failing tests для version/mode/userkey. Затем общий renderer и validator, привязки сохранённых URI и TUI с вариантами выбора. Внешние ссылки не усыновлять по совпадению IP. При смене серверных полей менять только явно связанные ссылки и точные их копии в группах; сохранять пользовательские названия, порядок, UUID, токены и дополнительные протоколы. Конфликт ревизии — отмена с повторным чтением.

### 3. Установка и восстановление — 1–2 дня

Проверить Debian 12/13 amd64, systemd, prerequisites, ELF/runtime, порт, свободное место, доступность Xray gateway до установки. Скачать и проверить все выбранные артефакты до остановки служб. Сделать backup; подготовить закрытую staging-конфигурацию; проверить её целевым бинарником. Права: root управляет конфигурацией, отдельная service group читает; ключи не попадают в argv/журнал.

После атомарной установки проверить процесс, listener и реальный запрос с тайм-аутом. Только затем публиковать URI новой конфигурации. Повторный запуск не генерирует PSK/userkey и не увеличивает revision без изменений. На ошибке восстановить согласованный набор бинарник/config/DB/routing/unit, показать результат rollback. Не восстанавливать всю устаревшую БД поверх параллельных правок: использовать блокировку/окно обслуживания либо проверяемое точечное восстановление.

### 4. Изолированная матрица — 1–2 дня

Прогнать сценарии ниже на обеих поддерживаемых Debian. Проверить реальный маршрут до контролируемого endpoint. Затем подготовить отчёт с командами, кодами выхода, хэшами и redacted логами. Не объявлять VPS-проверкой.

### 5. Разрешённый тестовый VPS + Android — отдельная команда, 0,5–1 день

После разрешения выбрать один узел, снять backup, добавить v6 без замены v5, записать исходные пользовательские данные. Импортировать созданную нашим установщиком ссылку в конкретный rc40 APK; провести матрицу на телефоне и повторную проверку v5. Публикация в двух репозиториях/Latest и установка на другие серверы — после приёмки и отдельной команды пользователя.

Итого основной TCP/UDP v6 с сохранением v5: ориентировочно **4–8 рабочих дней** одного разработчика, включая испытания. QUIC Proxy — отдельное исследование и оценка после выявления совместимой пары, без обещанного срока. Оценка не означает выполнение в этом исследовании.

## Обязательная матрица испытаний

| Проверка | Условие успеха |
|---|---|
| Чистая Debian 12 и 13 amd64 | Фактические service/listener, TCP/HTTPS/UDP проходят; выдаются верные URI |
| Повтор установки | Ключи, порты, имена и идентичности неизменны; нет дубликатов/лишнего bump revision |
| Обновление v5 установки | V5 остаётся работоспособным, новые компоненты не включаются самопроизвольно |
| Обновление уже включённого v6 | Preserved mode/users/route; обычный update не переключает wire-version |
| Недоступная загрузка, неверный hash, битый архив/ELF | Ненулевой exit до замены рабочих файлов |
| Неподдерживаемая версия/схема/ОС/архитектура | Понятная ошибка до изменений, без fallback на другой протокол |
| Занятый/запрещённый порт | Для нового endpoint выбрать свободный; для сохранённого конфликт показать, не менять реквизиты молча |
| Неверный config, нет gateway, service crash | Ограниченный timeout, восстановление; watchdog не скрывает ошибку установки |
| TCP | Echo с побайтовой проверкой, HTTPS по домену и IP с корректным SNI, half-close, параллельность |
| DNS/UDP | UDP DNS A/AAAA и STUN на контролируемый сервер; доменное и IP назначение; IP ответа правильно сопоставляется |
| Режимы v6 | default/unshaped/unsafe-raw × reuse false/true; mismatch не считается успехом; raw только в лаборатории |
| Аутентификация | Wrong PSK, userkey, отсутствие/отзыв ключа; отсутствие доставленного payload при отказе; другие пользователи работают |
| Длительность | Минимум 30 минут, периодические DNS/HTTPS/STUN, idle reuse, reconnect; учёт PID/FD/RSS и фактических ошибок |
| Маршрут | Direct и Xray отдельно; подтверждённый egress и трафик на gateway, отсутствие петель, v5 не затронут |
| QUIC Proxy | Только отдельная совместимая пара; QUIC Initial реально идёт по UDP к серверу, есть ответы/idle/reconnect/MTU; обычный STUN fallback не доказывает QUIC |
| Подписка/клиент | URI → импорт → сохранение → экспорт → повторная подписка; поля/имена/ID не теряются; v5 и v6 видны отдельно |
| Откат | Ошибка после каждого шага: до/после config, binary, unit, start, DB; исходный v5 и данные восстановлены |
| Остановленная служба | Update сохраняет намеренно остановленное состояние, не выдаёт его за отказ старта |

Локальные тесты не заменяют Android: на телефоне дополнительно проверить DNS/FakeDNS, переключение Wi-Fi/мобильной сети, остановку/повторное подключение, отсутствие оставшихся процессов и маршрут активного VPN. Указывать отдельно пропуски, повторные попытки и неудачи; не объединять fallback с успешным тестом выбранного транспорта.

## Решения пользователя и оставшиеся вопросы

Для подготовки реализации достаточно предложенных безопасных defaults: v5 сохраняется, v6 добавляется отдельно, default mode, QUIC Proxy выключен, Debian 12/13 amd64, текущий TUNA loopback-only. Дополнительные вопросы нужны только перед фактическими действиями:

- Команда начать реализацию и затем выбор разрешённого тестового VPS/времени приёмки.
- Если нужен перевод старого endpoint на v6 вместо дополнительной ссылки — явный выбор и согласованное окно разрыва совместимости.
- QUIC Proxy вместе с v6: либо отдельная подтверждённая реализация, либо изменение клиентского контракта агентом клиента. Сервер не должен сам подменять version.

До выпуска остаются непроверенными: соответствие release-бинарника Hydracore source commit, сборка выбранного минимального core на Debian 12, полный runtime userkey, оптимизированный QUIC Proxy, реальный rc40 против новой установки, лицензирование выбранного способа распространения. Ни один из этих пунктов не скрыт формулировкой «всё поддерживается».
