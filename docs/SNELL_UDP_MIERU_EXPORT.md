# Snell UDP и согласованный экспорт Mieru

Изменения рабочей ветки после `v2026.10.01.1`. Этот документ не означает,
что изменения уже опубликованы или установлены на всех серверах.
Поддерживаемая среда: Debian 12–13, amd64, systemd.

## Причины ошибок

Snell выполняет исходящие DNS-запросы от своего системного пользователя.
Прежний `snell-routing.sh` направлял TCP и UDP через NAT REDIRECT.
На тестовом узле UDP-слушатель Xray существовал, однако исходное назначение
превращалось в `127.0.0.1:12346`; правило блокировки private IP отклоняло запрос.
Это воспроизведено с фактическим бинарником Xray в отдельном network namespace.
На другом обследованном клиентским агентом узле REDIRECT-вход дополнительно
был настроен только на TCP. Простого добавления UDP в этот вход недостаточно.

Выбранная схема соответствует требованиям [Linux TPROXY](https://docs.kernel.org/networking/tproxy.html):
TCP сохраняет REDIRECT, а UDP проходит OUTPUT mark → policy routing → loopback
PREROUTING TPROXY → прозрачный UDP-вход Xray. DNS не получает отдельный DIRECT-обход.

Mieru: `extract_current_server_links()` добавляла в URI mode=48/right7,
независимо от protobuf `traffic-pattern`, полученного у работающей службы.
Индивидуальный экспорт отдельно читал файл конфигурации, который также мог
отличаться от состояния демона. Клиент обоснованно отклонял конфликт 32/48.

## Маршрутизация Snell

Авторитетная реализация — `scripts/snell-routing.py`; shell-файл вызывает её.
При установке Python-helper и `xray-discovery.py` копируются **до** запуска Snell.
Используются сохранённые порты из `/etc/x-manager/gateways.env`, UID пользователя
`snell`, mark `0x534e`, таблица и priority `1988`.

Перед изменением firewall проверяются конфигурация и слушатели шлюзов, UDP
`followRedirect`, `sockopt.tproxy=tproxy`, одинаковая политика маршрутизации для
REDIRECT/TPROXY, отсутствие конфликта policy slot, синтаксис правил ядром.
Ответы Snell, loopback и собственные адреса исключаются. Повторные исходящие UDP
в том же conntrack-потоке тоже маркируются. При конфликте или неполной
конфигурации операция завершается ошибкой до применения правил.

Файл `/etc/snell/tproxy-state.json` отмечает принадлежность таблицы/правила.
Нормальное применение изменяет только цепочки `SNELL_OUT`, `SNELL_MARK`,
`SNELL_TPROXY` и их hooks. Повторный запуск не создаёт дубликаты.
При частичном сбое восстанавливаются снимки NAT/mangle и прежнее состояние policy.
Резервные копии находятся в `/var/backups/x-manager-snell-routing-*`.

Для переключения режима меню вызывает:

```bash
/usr/local/bin/snell-routing.sh --mode xray
/usr/local/bin/snell-routing.sh --mode direct
```

`routing.mode` сохраняется только после успешного применения. При ошибке
записи возвращается предыдущая маршрутизация; ложного сообщения об успехе нет.
Обычный вызов без аргументов применяет уже сохранённый режим.

Общий откат установщика теперь сохраняет/восстанавливает Snell policy отдельно
от iptables. Чужие таблицы/правила не сбрасываются. Если принадлежность занятого
slot изменилась, откат сообщает об ошибке вместо перезаписи чужого состояния.
При восстановлении управляемый Xray/x-ui запускается до зависимых служб.

Ограничения: реализация относится к IPv4-пути. AAAA DNS-ответ по IPv4 не означает
проверку IPv6-сети. При `ipv6=true` без предусмотренного IPv6-шлюза операция
отклоняется. Разделённые Xray-конфиги, из которых нельзя однозначно определить
пару шлюзов и их общую routing policy, требуют отдельного согласования.
Не исправлять это отключением проверок.

## Единый экспорт Mieru

Оба пути TUI используют `scripts/mieru-subscriptions.py`:
индивидуальный экспорт и создание/пересборка подписки по явному действию пользователя.
Генератор получает конфигурацию демона через `mita describe config`, исходный
protobuf через `mita export traffic-pattern`, его JSON через штатный
`mita explain traffic-pattern` и эффективные параметры через
`mita describe effective-traffic-pattern`. Повторное чтение проверяет, что
конфигурация не изменилась в ходе экспорта. Ошибка RPC/декодирования не даёт
пустую или частично заполненную ссылку.

Пароль и выбранный пользователь берутся из того же снимка службы. Сохраняется
прежняя политика выбора первой portBinding и MULTIPLEXING_HIGH; никакие
параметры самой службы не меняются. Query-поля low entropy выводятся из
проверенной эффективной модели и сверяются с явно заданными полями protobuf.
URI корректно экранирует имена, пароли и Base64, включая `+`.

Экспорт содержит секреты: показывать его только владельцу либо сохранять
в закрытый файл, не в журнал CI или отчёт. Например, на разрешённом сервере:

```bash
umask 077
helper=/usr/local/share/x-manager/scripts/mieru-subscriptions.py
python3 "$helper" export --server-ip "$SERVER_IP" --user "$MIERU_USER" \
  --name 'Mieru-Home' > /root/mieru-export.private.txt
python3 "$helper" validate < /root/mieru-export.private.txt
```

`validate` допускает protobuf-only и query-only представления, но отвергает
противоречие при наличии обоих, неизвестные enum и дублирующиеся query-ключи.
Он не заменяет проверку подключения штатным адаптером клиента.

## Точечное исправление старой записи

Установщик **не** переписывает автоматически существующие Mieru URI.
Для будущего разрешённого ремонта существует `preview`/`repair`. Требуются:
явный путь БД из конфигурации TUNA, адрес сервера, ID пользователя, его текущая
ревизия и SHA-256 **одной выбранной строки URI без окружающих пробелов**.
Реквизиты выбранной строки, portBinding и декодированный protobuf должны
совпасть с работающей службой. Одного совпадения IP недостаточно.

Закрытый файл запроса содержит только:

```json
{"user_id":"ID_SELECTED_USER","revision":5,"uri_sha256":"SHA256_SELECTED_URI"}
```

Сначала preview; он не изменяет БД. Только после проверки результата и
разрешения на конкретный сервер выполняется repair с тем же запросом:

```bash
python3 "$helper" preview --database "$TUNA_DB" --server-ip "$SERVER_IP" \
  < /root/mieru-repair-request.private.json
python3 "$helper" repair --database "$TUNA_DB" --server-ip "$SERVER_IP" \
  < /root/mieru-repair-request.private.json
```

Исправляются только два redundant enum-параметра выбранной ссылки и её точные
копии в групповых профилях того же пользователя. Остальные байты ссылки,
ручные/внешние ссылки, другие пользователи, токены, IDs групп/профилей сохраняются.
Коллизия двух профилей или устаревшая ревизия приводит к отказу всей транзакции.
Ревизия изменённого пользователя увеличивается один раз.

До фиксации изменений SQLite backup API сохраняет БД с WAL-транзакциями в
закрытый `/var/backups/x-manager-mieru-*`. Там же `change.json` содержит
точный журнал одного изменения. Адресный откат не заменяет всю БД:

```bash
python3 "$helper" restore --database "$TUNA_DB" --backup "$REPAIR_BACKUP"
```

Он проверяет ревизию/содержимое после ремонта и отказывается затирать более
новые изменения пользователя или его групп. Возвращается прежняя ссылка,
а ревизия увеличивается, чтобы клиент получил изменение. Другие пользователи
и их изменения после резервной копии остаются нетронутыми. Откат возвращает
также прежнее противоречие, если оно было: использовать только для отмены ремонта.

## Установка, обновление и общий откат

Эта доработка пока не входит в опубликованный pinned quick-start.
Для разрешённой проверки использовать полный проверенный checkout с соседними
`scripts`, `bin`, `tuna-sub-server`, manifest и компонентами, а не отдельный install.sh:

```bash
# Чистая установка с заранее настроенными и работающими шлюзами Xray:
bash install.sh --quick
# Либо явно выбранный прямой выход на чистой системе:
bash install.sh --direct
# Обновление с сохранением данных:
bash install.sh --update
```

Сохранить напечатанные путь backup и команду отката. После установки проверить
активность служб, реальные DNS/HTTPS и итоговый ответ подписки. Не пересобирать
профили ради проверки. Общий откат выполняется командой, напечатанной установщиком:

```bash
bash /usr/local/share/x-manager/distribution/install.sh --rollback "$INSTALL_BACKUP"
```

Общий откат восстанавливает снимок управляемых файлов/БД/firewall и состояние
служб. Он может отменить изменения после снимка, поэтому сначала сверить
такую активность и выбрать подходящее окно. Установленные пакеты и системные
пользователи не удаляются.

## Тесты для дальнейшей разработки

Linux unit/regression:

```bash
python3 -m unittest discover -s tests
python3 -m unittest discover -s tuna-sub-server/tests
```

Для новых Mieru-тестов нужен закреплённый `mita` в PATH: тестируется настоящий
protobuf codec. Все реквизиты тестов синтетические.

`tests/lab-snell-network.py` требует root и отдельный network namespace:

```bash
unshare -n python3 tests/lab-snell-network.py /path/to/tested/xray
```

Он воспроизводит старый UDP REDIRECT-дефект, проверяет исправление, повторный
UDP в одном сокете, direct/xray, коллизии и частичный откат. В чистом namespace
проверяет реальное восстановление policy rule/table общим rollback-helper.

Только в специально помеченной одноразовой Debian/systemd-лаборатории:
`lab-clean-release.py`, `lab-upgrade.py`, `lab-failures.py`,
`lab-persistent-rollback.py`, `lab-mieru-export.py`, `lab-snell-installer.py`.
Последний требует тестовый Xray в `/opt/snell-network/xray` и проверяет
настоящий update, отказ службы и возврат из активного TPROXY в исходный direct.
Эти тесты изменяют свою лабораторную установку; не запускать на VPS.
