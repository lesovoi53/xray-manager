# ТЕХНИЧЕСКАЯ ДОКУМЕНТАЦИЯ И ЖУРНАЛ РАЗРАБОТКИ
## Мультитранспорт OpenFlux (Яндекс Доски / Multi-Stream PR #56), WebDAV PROPFIND диагностика и реорганизация X-Manager

---

### 1. ОБЩИЕ СВЕДЕНИЯ И ЦЕЛИ РАЗРАБОТКИ

Данный документ фиксирует архитектурные решения, изменения в кодовой базе и регламент обслуживания для передачи контекста последующим разработчикам и ИИ-агентам.

#### Задачи этапа:
1. **Реорганизация интерфейса X-Manager:**
   - Перевод главного меню (`main_hub`) и сводной карточки статуса на 4 логических блока с непрерывной сквозной нумерацией `[1]–[14]`.
   - Синхронизация нумерации карточек сервисов и пунктов меню.
2. **Внедрение транспорта Яндекс Доски (`boards.yandex.ru`):**
   - Интеграция протокола WebSocket Engine.io v4 досок Яндекса с обходом капчи и туннелированием L4-пакетов через `notify-position`.
3. **Гибридный Multi-Stream транкинг:**
   - Объединение 8 изолированных systemd-каналов `openflux@1..8` с агрегацией до 4 облачных документов на один канал на уровне протокола (патч PR #56).
4. **Интерактивная диагностика и префлайт-чекеры:**
   - Экспресс-тест WebDAV-аккаунтов методом RFC 4918 `PROPFIND` (`Depth: 0`).
   - Экспресс-тест ссылок OpenFlux (проверка прав редактирования `canEdit: true`, приватности/редиректов в `passport.yandex.ru`, валидности токенов Досок).

#### 2.1. Реорганизация меню диспетчера (`bin/x-manager`)

|---|---|---|---|

#### 2.2. Транспорт Яндекс Доски (`boards.yandex.ru`)

В репозитории `p1neappleXpress/OpenFlux` реализован модуль `transport/yandex/boards.go` (коммиты `38782b2b` и `d13aa5b7`):
- **Схема подключения:** 
  1. Выполняется GET-запрос страницы `https://boards.yandex.ru/whiteboard/?hash={HASH}`.
  2. Извлекается токен доступа `token` и идентификатор сессии.
  3. Устанавливается соединение WebSocket с `wss://socket33.boards.yandex.ru/socket.io/?EIO=4&transport=websocket`.
  4. Клиент подписывается на сессию: `42["subscribe-slide-dashboard", ...]`.
  5. Передача данных осуществляется в событии `notify-position`: полезная нагрузка кодируется в Base64 и помещается в координаты курсора `data.position.x` и `data.position.y`.
- **Обход капчи (`captcha.go`):**
  При получении редиректа на `showcaptchafast` транспорт обращается к эндпоинту валидации и автоматически получает сессионную куку `spravka`, обходя блокировку без участия пользователя.
- **Поддержка в X-Manager:**
  - Функция `detect_transport_from_url` распознает ссылки вида `*boards.yandex.ru*` и присваивает транспорт `boards`.
  - В меню каналов OpenFlux добавлена возможность ручного выбора `boards`.
  - В скриптах маршрутизации `openflux-routing.sh` добавлены подсети Яндекса (`5.45.192.0/18`, `77.88.0.0/18`, `87.250.250.0/24`, `93.158.134.0/24`, `178.154.131.0/24`, `213.180.193.0/24`), чтобы трафик WebSocket Досок не замыкался в Xray REDIRECT.

#### 2.3. Гибридный Multi-Stream транкинг

В системе реализовано 2 уровня агрегации:
1. **Системный уровень (OS Level):**
   - До 8 независимых systemd-сервисов `openflux@1` — `openflux@8`.
   - Каждый инстанс имеет изолированный `.env`-конфиг в `/etc/openflux/instances/{N}.env`.
   - Возможность разделения по разным провайдерам (Яндекс Волга, Доски, Mail.ru, Cups.online).
2. **Протокольный уровень (Stream Bonding, PR #56):**
   - Патч `patches/openflux-multistream.patch` интегрирован в исходный код OpenFlux.
   - Параметр `--url` принимает список URL через запятую (например, `URL="https://docs.yandex.ru/...,https://boards.yandex.ru/..."`).
   - Модуль `MultiStreamTransport` выполняет хэширование потоков (flow-hashing по 5-tuple: IP источника/назначения, порты, протокол). Пакеты одной TCP-сессии передаются через один документ (устраняя jitter и out-of-order пакеты), а параллельные сессии балансируются между всеми документами.
   - В случае блокировки или разрыва одного документа происходит мгновенный бесшовный failover на доступные документы из пула.
   - Поддерживаются транспорты: `vyandex`, `boards`, `mailru`, `yandex`.

#### 2.4. Механизм тестирования и валидации ссылок

##### А. WebDAV Экспресс-тест (`test_all_webdav_accounts`)
- Проверяет доступность серверов методом RFC 4918 `PROPFIND` с заголовком `Depth: 0` и Basic Auth:
  ```bash
  curl -s -m 5 -X PROPFIND -H "Depth: 0" -u "USER:PASS" "URL"
  ```
- Коды ответа:
  - `HTTP 207 Multi-Status` — Авторизация успешна, хранилище готово к приему трафика.
  - `HTTP 401 Unauthorized` — Неверный логин или пароль (требуется пароль приложения).
  - `HTTP 403 Forbidden` — Включена 2FA без пароля приложения либо WebDAV отключен на аккаунте.
  - `HTTP 000` / таймаут — Сетевая недоступность или блокировка порта.

##### Б. OpenFlux Экспресс-тест (`test_all_openflux_channels`)
- Для ссылок **Multi-Stream** автоматически разбирает список по запятым и тестирует каждый документ по отдельности (`[Док #1/N]`, `[Док #2/N]`).
- Для **Яндекс Документов (Волга / OnlyOffice):**
  - Обнаруживает редиректы на `passport.yandex.ru` (документ приватный, не открыт доступ по ссылке).
  - Проверяет HTML-тело на атрибут `"canEdit":false` (документ доступен только на чтение, запись невозможна).
  - Фиксирует вызов `showcaptchafast` (сработает автообход).
- Для **Яндекс Досок (`boards.yandex.ru`):**
  - Проверяет наличие обязательного параметра `?hash=...`.
  - Выполняет HTTP-запрос к доске и валидирует статус `200/302`.
- Для **Mail.ru Документов:**
  - Проверяет доступность публичной ссылки документа.

Оба чекера вызываются:
- Горячей клавишей `[T]` в подменю WebDAV Tunnel и OpenFlux.
- Автоматически в виде pre-flight проверки при вводе новых учетных данных или ссылок.

#### 2.4. Два архитектурных режима OpenFlux (Классический балансир 8×1 ↔ Multi-Stream 8×4)
В `menu_openflux` реализован интерактивный переключатель архитектуры через горячую клавишу `[M]` с **полной изоляцией ссылок и профилей каналов**:
1. **Режим 1: Классический балансир (8×1)**:
   - 8 независимых каналов связи (`openflux@1` .. `openflux@8`).
   - На каждый канал выделяется ровно 1 облачный документ (Яндекс Волга, Яндекс Доски, Облако Mail.ru).
   - Ссылки хранятся в изолированном профиле `/etc/openflux/profiles/classic/`.
   - Максимальная изоляция сбоев: падение одного документа затрагивает только 1/8 сессий.
2. **Режим 2: Multi-Stream транкинг (8×4, PR #56)**:
   - 8 транковых каналов связи (`openflux@1` .. `openflux@8`).
   - В каждый канал передаётся от 1 до 4 ссылок через запятую (`url1,url2,url3,url4`), суммарно до 32 документов в пуле.
   - Ссылки хранятся в изолированном профиле `/etc/openflux/profiles/multistream/`.
   - Flow-hashing сессий внутри каждого канала, агрегация пропускной способности и мгновенный failover без разрыва TCP.

**Изоляция профилей при переключении `[M]` (`switch_openflux_pool_mode`)**:
- При переходе между режимами текущие ссылки каналов автоматически сохраняются в профиль активного режима и выгружаются.
- Загружаются ссылки выбранного режима из его персонального профиля. Ссылки режимов **не смешиваются, не затираются и не переносятся** из одного режима в другой.
- Службы `openflux@1..8` перезапускаются: каналы с заданными ссылками стартуют, каналы без ссылок выключаются.

Текущий режим отображается:
- В главном дашборде `main_hub()`: карточка `[4] 📡 OpenFlux [Классический балансир (8×1) / Multi-Stream (8×4)]`.
- В блоке 1 `main_hub()`: `[4] 📡 Управление OpenFlux [Классический балансир (8×1) / Multi-Stream (8×4)]`.
- В заголовке меню OpenFlux: строка `Архитектура: ...`.
- В пункте меню `[M] 🔀 Архитектурный режим: [1] Классический балансир (8×1) ↔ [2] Multi-Stream (8×4, PR #56)`.
#### 2.5. Исправление протокола Яндекс Досок (Yandex Boards HTTP 415 -> JSON API)
В сентябре 2026 года Яндекс обновил внутренний API Яндекс Досок (`https://boards.yandex.ru/api`):
- Старый протокол `application/x-www-form-urlencoded` с base64-пейлоадом стал возвращать ошибку `HTTP 415: Request body must use a JSON Content-Type`.
- Функции `postAPI` и `getWhiteboardInfo` в `transport/yandex/boards.go` обновлены на строгий `Content-Type: application/json; charset=utf-8` с передачей нативного JSON-объекта `{"action": "...", "content": {...}}`.
- Изменение интегрировано в патч `patches/openflux-multistream.patch` и собрано в бинарник `/usr/local/bin/openflux`.
- Результат: Канал 3 (Яндекс Доски в режиме Multi-Stream на 4 документа) успешно авторизуется через WebSocket и работает в статусе `[АКТИВЕН]`.
