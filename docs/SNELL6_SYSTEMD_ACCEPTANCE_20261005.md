# Локальная проверка службы Snell v6

5 октября 2026: итоговая серия **6/6 прошла за 15,42 с**. Среда — существующий изолированный Debian 13 nspawn под WSL, systemd 257.13, private-network. Рабочие VPS и установщик не менялись.

Проверялся временный `xm-snell6-qa.service`, отдельный от действующего Snell v5. Использован ранее проверенный Linux sing-box-extended 2.7.2, пользователь `snell`, конфигурация root:snell 0640 в каталоге 0750, синтетический PSK. Юнит содержит Type=exec, ExecStartPre=check, Restart=on-failure, RestartSec=1, StartLimitIntervalSec=infinity, StartLimitBurst=3 и базовые ограничения NoNewPrivileges/PrivateTmp/ProtectSystem/ProtectHome.

| Сценарий | Результат |
|---|---|
| Корректная конфигурация | Процесс работает от непривилегированного UID; TCP listener действительно принимает соединение |
| Ручная остановка | MainPID=0, прежний PID отсутствует, самоперезапуска нет |
| Неверный JSON | `systemctl start` возвращает ошибку, журнал содержит причину; процесс службы не запущен |
| Занятый порт | Ошибка bind `address already in use`, служба переходит в failed после ограниченных попыток |
| Три принудительных падения | Первоначальный запуск плюс два успешных автоперезапуска; следующая попытка запрещена лимитом, все три PID завершены |
| Явный reset-failed и запуск | После сброса лимита служба снова запускается |

`NRestarts=3` включает назначенную, но заблокированную лимитом попытку. Это не три успешных автоперезапуска. На данном systemd при исчерпании лимита Result сохраняет `signal`/`exit-code`; журнал содержит `Start request repeated too quickly`. Для диагностики нужны также счётчик, фактические PID и отсутствие последующего запуска, а не только сравнение Result со строкой start-limit-hit.

## Обнаруженное при подготовке стенда

Первый запуск обнаружил реальный отказ доступа: лабораторный бинарник находился в каталоге 0700, недоступном UID службы; systemd сообщил 203/EXEC. Для тестового юнита бинарник скопирован в отдельный доступный каталог, режим конфигурации сохранён 0640. Это исправление стенда, не обнаруженная ошибка опубликованного установщика.

Вторая попытка выявила особенность обвязки: systemd выгружал неактивный временный юнит, и reset-failed возвращал ошибку. Итоговый тест явно включает временный юнит, а при завершении выключает и удаляет его. Третья серия проверила фактическое ограничение рестартов, но её проверка ошибочно ожидала Result=start-limit-hit; итоговый тест исправлен на наблюдаемое поведение, подтверждённое журналом. Ранние результаты сохранены в отдельных каталогах лаборатории, не выданы за успешные.

## Артефакты и границы

- [Тест](../tests/lab_snell6_systemd.py): запускается только при маркере лаборатории, nspawn и Debian 13; существующий одноимённый юнит не перезаписывает.
- [Итоговый JSON](SNELL6_SYSTEMD_RESULTS_20261005.json).
- Точный проверенный юнит и журнал: `/opt/xm-snell6-systemd-qa-v4/` внутри локального rootfs `/var/tmp/x-manager-debian13-lab/rootfs`.

Тестовая конфигурация и systemd-юнит удалены; в финале MainPID=0. Контейнер после сохранения отчёта выключен. Юнит не интегрирован в меню, установщик или allowlist TUNA watchdog. Лимит проверен непосредственно средствами systemd и соответствует схеме attempts+1 существующего watchdog; его UI/API здесь не тестировались.

Проверка слушателя не заменяет сетевые испытания: TCP/HTTPS и UDP ранее проверены отдельными стендами. Не проверены загрузка настоящего VPS, reboot persistence, обновление/откат установщика, Android и длительная работа. Политику двух рестартов использовали для короткого теста; значение для будущего установщика должно быть настраиваемым.
