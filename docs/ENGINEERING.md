# Контракты и порядок дальнейшей разработки

Для `v2026.10.11.0-rc1`; документация от 11 октября 2026.
[Карта модулей и сборка](DEVELOPMENT.md) · [Пользовательские сценарии](OPERATIONS.md)

## Граница проекта

X-Manager оркестрирует готовые серверные ядра и существующий Xray, хранит
конфигурации и формирует подписки. Клиент TUNA, обработчик сторонней панели,
внешние API облаков, DNS-делегация и правила хостинга — отдельные системы.
Поддержка протокола ядром не равна поддержке URI клиентом или поддержки
всех параметров этого ядра нашим интерфейсом.

Не добавляйте ARM64, QUIC Proxy, индивидуальный учёт общего Snell PSK или
автоматическое изменение чужой панели как «попутное улучшение». Объём принятой
серверной реализации — Debian 12/13 amd64, сохранение действующих данных,
совместимые закреплённые компоненты и явные настройки пользователя.

## Слои и источники истины

```text
components.json -> release-assets.py -> проверенные файлы компонентов
                                    -> install.sh -> snapshot/validate/commit
bin/x-manager -> menu-v2.sh -> специализированные helpers -> config + systemd
службы -> локальные шлюзы Xray / Direct -> исходящий трафик
локальные configs -> генераторы/синхронизаторы -> TUNA SQLite -> HTTP formats
                                                          -> агрегатор -> клиент
```

| Данные | Владелец и правила |
|---|---|
| Версия бинарника и checksum | `components.json`; обновляются вместе с проверенным asset |
| Локальный endpoint | Конфигурация конкретной службы; helper валидирует и применяет |
| Намерение start/stop/off | `service-control.py`, `/etc/x-manager/service-control`; приоритет над watchdog |
| Каталог TUNA | Сервер подписок; импорт не должен перезаписывать несвязанные внешние записи |
| Выбор и порядок пользователя | База TUNA, пользовательские ID/revision; не выводить из «всех активных» при каждом чтении |
| Группы автовыбора | `tuna_connection_groups.py`; полный атомарный snapshot с expectedRevision |
| Счётчики аварий | systemd и собственные state-файлы по виду восстановления |
| Результат теста канала | Фактическая проверка клиента/сети; не подменять значением ActiveState |

Не копируйте таблицу как полный allowlist отката. Источник точного списка —
`installer-state.py`: там также обрабатываются переопределённые пути и состояние
служб. Резервная копия конфигурации WebDAV не равна резервной копии всего его
пользовательского хранилища. Пакеты ОС и системные аккаунты не откатываются
как полный образ VPS.

## Установка, ошибка и восстановление

- `xm_preflight` проверяет поддерживаемую систему до рабочих изменений.
- План портов учитывает текущие значения и реальные слушатели. Не заменяйте
  сохранённый порт случайным свободным, чтобы скрыть несовместимый gateway.
- Каждый скачанный компонент проверяется по SHA256. Ошибка источника не должна
  переключать на upstream main/latest или другой релиз без явного выбора.
- Перед заменой управляемых рабочих файлов создаётся и проверяется снимок.
- Валидация конфигурации, реальные состояния units и контроль API имеют разные
  роли; успешный `systemctl start` может означать skipped, проверяйте результат.
- При ошибке после начала транзакции восстановление должно сообщать отдельно
  о первичном сбое и о результате отката. Нельзя писать «успех» после неудачного restore.
- При повторном обновлении разрешённый запуск ранее активной службы может требовать
  `reset-failed`. Он выполняется после проверки lifecycle, не вместо неё.
- Не сбрасывайте persistent-бюджет OpenFlux или ручное off ради повторной установки.
- Не удаляйте marker обслуживания, не доказав восстановление внешнего владельца.
  Для штатного продолжения существует `install.sh --recover-watchdog`.

Старый polling `tuna-watchdog.timer` и современный recovery timer — разные units.
Миграция старого polling-механизма требует предусмотренного флага
`--update --migrate-legacy-watchdog`, а не удаления всех файлов со словом watchdog.
Внешний `vpn-watchdog` — ещё один отдельный владелец. Его отсутствие — нормальное
условие, собственные политики и recovery должны работать без него.

## Контракт выдачи подписок

1. Не менять входные внешние URI с неизвестными параметрами ради косметической
   нормализации. Привязанные локальные URI формируются общим генератором.
2. Сохранять пользователя, UUID, subscription token, connection ID и issuer.
   Увеличивать revision при изменении выдаваемых данных, а не при каждом чтении.
3. API экспорта OpenFlux содержит вложенный `payload`. Предпросмотр имени,
   mode и groups должен читать его, иначе UI может показать defaults при правильном URI.
4. Внешний OpenFlux bundle добавляется отдельно. Нельзя заменять локальный bundle
   только потому, что оба используют один transport или одинаковое имя группы.
5. Для WebDAV изменение шифрования проходит конфиг → точное сопоставление каталога
   → затронутые пользователи/revision → URI. Проверять не только runner.
6. Для Mieru `traffic-pattern` содержит Base64 внутри URI: `/` и `=` остаются
   буквальными по согласованному генератору; `+` кодируется `%2B`. Не вводить
   повторное percent-encoding и не отключать маску ради импорта.
7. Snell v5/v6 переключаются транзакционно; выдача локального endpoint учитывает
   активную версию. Внешние ссылки не исчезают при переключении локальной службы.
8. Схема групп и пределы — в [CONNECTION_GROUPS_RC11.md](CONNECTION_GROUPS_RC11.md).
   `tuna-groups://v1/` — контейнер документа, а не новый VPN-протокол.
9. Внешний контейнер Base64URL JSON не является шифрованием. И URI, и исходный
   JSON считаются секретами. Не включать их в диагностические traceback/логи.

Проверяйте весь путь: config → генератор → запись пользователя → HTTP endpoint
→ внешний агрегатор → импорт клиентом. На каждом слое сравнивайте только нужные
поля/хеши, не печатайте весь секретный payload в публичный отчёт.

## Watchdog и конкуренция

Политика обычной службы хранится в `90-tuna-watchdog.conf`. Recovery признаёт
только свой строгий формат и managed header: это предохраняет чужие drop-in от
автоматического изменения. Новая версия формата требует явной миграции и тестов.

`Recovery.tick()` не обрабатывает каналы OpenFlux как независимые обычные units;
для них вызывается `Watchdog.recover()`. Иначе один сервер получил бы восемь
независимых бюджетов вместо общего и мог бы учесть одну попытку дважды.

Обычное восстановление проверяет распознанную политику, lifecycle, failed,
исчерпание, отсутствие mask и внешнего конфликта. Время следующей попытки
сохраняется атомарно до команд reset/start, чтобы прерывание не породило
неограниченный цикл. JSON проверяется по типам, размеру, конечности времени и
именам разрешённых unit; путь не должен неожиданно стать symlink.

Проверки зависаний не должны стартовать выключенные пользователем службы.
Нельзя считать любой неуспешный HTTP внешнего облака зависанием процесса
или расширять scope рестарта до всей панели без явного решения.
Перезапуск X-UI способен затронуть все его подключения, поэтому его пауза отличается.

## Как добавлять изменение

### Новая настройка существующей службы

Определить место хранения и значение по умолчанию → добавить валидацию →
сохранить совместимость существующего файла → реализовать UI через helper →
проверить config и запуск → обновить генератор/подписку при необходимости →
добавить round-trip и rollback/regression тесты → описать пределы.

### Новый компонент или unit

Добавить проверенный asset/version/hash и лицензию → preflight → конфиг/права →
unit/runner → snapshot/restore allowlist → lifecycle → opt-in watchdog → UI →
экспорт при наличии контракта клиента → чистая и повторная установка.
Не считать текст в меню доказательством поддержки. Не запускать пустые экземпляры.

### Перенос upstream-исправления OpenFlux

Записать точный source commit, затронутые carriers и wire changes → получить
минимальную воспроизводимую ошибку → перенести ограниченный патч на нашу базу →
применить строгую последовательность `build-openflux.sh` → `go test ./...` →
контроль размера/памяти/reconnect/heartbeat → собрать повторно и сверить хеш →
проверить совместимость клиента на разрешённых документах → обновить manifest.

Перенесённые в октябре исправления исходят из `74cac6d47bf4c27947348ee957538a2c0728a485`.
Это не переход всего проекта на свежий upstream. Mail.ru WebSocket использует
`OpenFlux/1.0`: исправление HTTP409 не означает замену всех API-заголовков.
Новые upstream handshake/crypto/fallback нельзя включать автоматически.
Полный исходный архив, патчи и [атрибуция](../ATTRIBUTION.md) должны оставаться доступны.

## Матрица приёмки

| Изменение | Минимальный локальный слой | Следующий необходимый слой |
|---|---|---|
| Текст меню/документация | Diff, ссылки, имена обработчиков | Ручная читаемость; нет необходимости перезапускать VPS |
| URI/подписка | Generator, export/import round-trip, HTTP, revision | Импорт конкретной сборкой клиента; внешний агрегатор отдельно |
| Watchdog | Искусственное время, конкуренция, stop/off, corrupted state | Реальный systemd и реальное ожидание cooldown |
| Установщик | Preflight/allowlist/restore tests | Чистая VM, повтор, update, инъекция отказов, реальный rollback |
| Маршрутизация | План портов, существующий config, правила | Настоящие TCP и UDP, путь/egress, сохранение чужих правил |
| Carrier | Handshake/framing/reconnect/лимиты буферов | Разрешённый документ + сервер + совместимый реальный клиент |
| Ресурсы | RAM/cgroup fixtures, сохранение override | Нагрузка, RSS/cgroup и влияние на соседние службы |

Основные наборы: `tests/test_installer_*`, `test_service_control.py`,
`test_openflux_watchdog.py`, `test_tuna_recovery.py`, `test_watchdog_health.py`,
`test_network_profile.py`, `test_openflux_resources.py`, `test_mieru_subscriptions.py`,
`test_snell*.py`, `test_webdav*.py`, `tuna-sub-server/tests`.
Запуск всех unit-наборов и shell syntax описан в [DEVELOPMENT.md](DEVELOPMENT.md).
Linux-зависимые тесты требуют Linux; успешный импорт Python в Windows их не заменяет.

`tests/lab-*` намеренно нарушают конфигурации/службы. Использовать только
изолированную лабораторию с `/.x-manager-test-lab`, не рабочий сервер.
Маркера самого по себе недостаточно: оператор должен проверить, что это
действительно отдельная VM/namespace без производственных данных.

Текущие доказательства: [чистая установка/отказы/откат](VERIFICATION_20261011_STEPS_1_4.txt),
[семь обновлений](FLEET_20261011.txt). Остались отдельными проверками Debian 12
в новом цикле, полный UDP-прогон, длительная нагрузка и Волга. Состояние клиента
не фиксируется навсегда этим документом; проверять конкретный APK/commit.

## Публикация и экономный цикл работы

1. Узкая задача, один воспроизводимый симптом, зафиксированные неизменяемые данные.
2. Целевой регрессионный тест и исправление причины; затем затронутые наборы.
3. При изменении установщика — VM до VPS; никаких массовых production экспериментов.
4. Сохранить отчёт: commit, manifest/архив hash, ОС, сценарий, результат,
   непройденные границы, команда отката. Исключить секреты.
5. Проверить remote HEAD, staged diff и лицензионные файлы. Отправлять без force-push.
6. Draft release должен содержать полный архив, SHA256SUMS и все manifest assets.
   Сверить хеш каждого, затем публиковать Latest. Только push в main не обновляет VPS.
7. Не заменять бинарники и SHA опубликованного выпуска под прежним тегом.
   Новая runtime-правка требует нового тега. Документацию можно обновить отдельно
   и приложить отдельным архивом, явно указав её commit и базовый runtime tag.
8. Проверить GitHub `/releases/latest` и доступность файлов. Обновления серверов
   выполнять только в разрешённом объёме, последовательно с контрольными снимками.

Не гонять весь набор повторно для изменения только текста. Не исследовать
неизменённые модули без симптома. Беречь бюджет на воспроизведение, проверку и
публикацию; метрика общего аккаунта не доказывает точную стоимость одной задачи.
