# Snell v6 → SOCKS5 Xray: локальная приёмка

5 октября 2026. **40/40 проверок прошли за 22,53 секунды.** Одна серия в Debian 13 userspace под WSL, отдельные mount/PID/network namespaces, только loopback. Никаких VPS, панелей или рабочих настроек.

## Схема

Тестовый запрос → локальный SOCKS клиента → Snell v6 default → серверный SOCKS outbound → Xray SOCKS5 inbound с UDP → локальный HTTPS/DNS/STUN fixture.

Сервер Snell имеет единственный SOCKS outbound; несмотря на унаследованное в тесте имя тега `direct`, его **тип — socks**, прямого outbound нет. Xray имеет единственный freedom outbound к тестовому сервису. Это тест предлагаемой интеграции, не результат изменения установщика.

## Повторение и границы

[Тест](../tests/snell6_local_acceptance.py) расширен необязательным `--xray PATH`. Без этого параметра сохранён прежний прямой сценарий. Для повторения использовать новый каталог `--out` и отдельную network namespace. [Машиночитаемый результат](SNELL6_XRAY_RESULTS_20261005.json). Обвязка и журналы: `snell6-xray-lab-20261005/` в родительском workspace.

DNS/STUN — контролируемые fixtures. Доменное HTTPS-назначение на серверной стороне Snell заменяется на loopback с сохранением порта; внешнее разрешение домена Xray не проверено. AAAA проверяет ответ DNS, не IPv6-доставку. SOCKS gateway локальный и без авторизации; защищённый SOCKS, UDP по доменному адресу, пользовательские правила Xray и реальный удалённый egress не проверены. TCP/UDP SOCKS-путь не равнозначен REDIRECT/TPROXY.

**Вывод:** для проверенной конфигурации Snell v6 default можно направить TCP и обычный UDP relay через SOCKS5 Xray. Следующие отдельные этапы — реализация установщика, systemd, обновление/откат и Android против этого Linux-сервера. Публикация и развёртывание не выполнялись.
